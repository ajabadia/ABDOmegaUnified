3. Aplicar las convenciones de modulación por rol
En este MVP modular no quieres todavía exponer el modulationGraph completo, así que usa roles para las conexiones:

envelope.role == "amp" → conectar su salida al VCA de la voz (amp envelope).

envelope.role == "mod" → conectar su salida al cutoff del filtro, escalada por layerParams.envAmount.

lfo.role == "mod" → conectar su salida al cutoff del filtro, escalada por layerParams.lfoAmount.
​

Conceptualmente, EngineConfigManager:

Busca envelopes con role:"amp" y role:"mod".

Busca LFOs con role:"mod".

Rellena en EngineConfig la estructura de modulaciones estándar:

modAmpEnv → VCA, modEnv → cutoff, LFO → cutoff.

Más adelante puedes migrar esto al ModulationGraph, pero ahora te basta con estas conexiones “hardcoded” a nivel de configuración.

4. Integrar con la polifonía y el snapshot engine
polyphony de la layer A determina cuántas voces del VirtualAnalogEngine instancias.
​

La arquitectura “atomic snapshot engine” que ya tienes para VA/ACE debe también servir aquí:

El EngineConfig construido desde ACE+preset se convierte en un snapshot que puedes swappear atómicamente sin locks.
​

Eso significa que cambiar de un preset Juno a uno VA modular no requiere código nuevo en el procesado, solo un EngineConfig distinto.

5. Qué validar en esta primera iteración
Antes de tocar UI:

Dado un preset de ejemplo con el shape modular que definimos, EngineConfigManager debería ser capaz de:

Construir un EngineConfig VA modular sin punteros nulos ni dependencias circulares.

Crear voices que suenen (osc→filter→VCA) con sus envelopes y LFO aplicados como se espera.
​

Los tests que ya definiste en VAACETESTPLAN.md para VA/ACE se pueden ampliar con 1–2 casos “VA modular” (preset simple Juno‑like y un MS20‑like) para confirmar que el motor se comporta.



Para cerrar el MVP del modo modular, te propongo una UX muy contenida: un “modo VA Modular” que se siente como un sinte clásico, no como VCV Rack.

1. Dónde se activa el modo modular
No añadas un botón “Modular” suelto: haz que venga implícito por el preset.

En la WebUI (rack inferior), la sección de motor muestra una pestaña o selector de “Engine”:

Objetivo: que el usuario no “vea” ACE ni el grafo; solo un VA moderno con un panel limpio.

El usuario selecciona “VA Modular” y carga/guarda presets que internamente usan el shape modular que definimos (1 osc, 1 filtro, env+LFO).

La UI no enseña componentId ni “slot 1/2”:

Para el MVP, cada preset modular puede cambiar internamente el oscilador/filtro ACE, pero el panel sigue mostrando los mismos controles lógicos (Osc Type, Filter Type, etc.), con opciones limitadas.

Más adelante, si quieres, podrías añadir una pequeña lista desplegable “Osc model / Filter model” que cambie el componentId ACE, pero no es necesario para arrancar.

4. Integración con el resto del rack
Mantén el layout actual de doble rack: arriba utilidades (scope, MIDI viewer, etc.), abajo síntesis.

Cuando el preset es VA Modular:

Sustituye el combo de módulos Juno/JP/Korg por el único módulo “VA Modular”.

Deja Space Echo u otros FX como están; el usuario puede seguir viendo/ajustando FX encima del motor.
​

Así no cambias la arquitectura visual, solo qué “bloque de motor” se dibuja.

5. MVP sin edición de arquitectura, solo de parámetros
Para esta primera versión modular:

El usuario no edita conexiones ni el “voiceArchitecture”:

No puede añadir otro osc, ni otro filtro, ni cambiar roles de env/LFO.

Solo toca parámetros de panel y, si lo implementas, un selector de modelo de osc/filtro.
​

La edición de arquitectura (añadir otro oscillador, elegir otro envelope, etc.) la dejas para una Fase 2, quizá bien integrada con el futuro editor de ModulationGraph o un editor de “voice architecture” aparte.
​

Con esto consigues:

Un modo “VA Modular” que ya usa todo tu stack ACE/EngineConfig,

pero que a ojos del usuario es solo “otro motor VA” con un panel fino, sin abrir aún el melón de patching modular tipo Eurorack.



Para una futura edición de arquitectura modular, te propongo una pantalla específica de “Voice Architecture” que no toca el MVP actual, pero encaja con tu stack ACE/ModulationGraph.

1. Entrada al editor de arquitectura
Desde el módulo “VA Modular” añade un botón discreto tipo “Edit Architecture…”.

Eso abre una vista aparte (modal grande o pestaña nueva) donde ya no ves knobs, sino bloques lógicos: Osc, Filter, Env, LFO, FX.
​

El preset sigue sonando; esta vista es puramente de diseño estructural, no de performance inmediata.

2. Layout conceptual de la vista
Piensa en tres paneles:

Panel izquierdo: Biblioteca ACE

Lista agrupada de componentes permitidos:

Oscillators VA, Filters VA, Envelopes genéricos, LFOs, FX simples.
​

No todo el catálogo ACE: solo la “whitelist modular” para no abrumar.

Zona central: Arquitectura de voz

Vista en columnas:

Columna “Oscillators” con hasta 3 slots.

Columna “Filters” con 1–2 slots en serie o paralelo.

Columna “Envelopes” (AMP, MOD1, MOD2).

Columna “LFOs”.

Panel derecho: Detalles del bloque seleccionado

Lista simple de parámetros ACE relevantes para ese componente (no panel completo, solo lo esencial de arquitectura: p.ej. modo del filtro, número de polos, etc.).

3. Operaciones que permite (Fase 2, no MVP)
Mantén las operaciones muy acotadas:

Osciladores:

Añadir/quitar hasta un máximo (por ejemplo 3).

Flag simple “enabled” y quizá “blend role” (main/sub).

Filtros:

Envelopes:

Fijar roles: AMP, MOD1 (filtro), MOD2 (libre).

Añadir hasta 3 envelopes genéricas.

LFOs:

Añadir hasta 2 LFOs globales de voz.

Roles: vibrato, mod filtro, libre.

Nada de patch cables ni grafo todavía; las conexiones siguen siendo por convención de roles (como ahora) o se delegan a modulationGraph más adelante.

4. Cómo se refleja en el preset
Esta vista edita directamente la sección voiceArchitecture del YAML:

Listas oscillators[], filters[], envelopes[], lfos[] con sus componentId, enabled, role y parámetros clave.

EngineConfigManager reconstruye un nuevo EngineConfig VA y lo swappea atómicamente.
​

La UI de panel (Module VA Modular) sigue mostrando el mismo conjunto de controles lógicos (cutoff, env amount, etc.), aunque por debajo haya ahora 2 oscs o 2 filtros; esos controles pasan a manejar “macro” de la arquitectura resultante.

5. Relación con ModulationGraph (futuro)
Más adelante, podrías añadir una pestaña secundaria “Advanced Routing” que abra el editor del ModulationGraph para ese preset, donde las salidas de LFO/ENV/ModSources ya estén instanciadas como nodos.

En esta Fase 2 de arquitectura, sin embargo, el usuario sólo decide qué componentes hay y sus roles; el patching fino lo dejas para el grafo o para convención.

Con este diseño, el MVP sigue siendo un VA “normal”, y la edición de arquitectura se siente como una herramienta de power users separada, sin convertir todo el sinte en un entorno modular caótico.
